# JSON Table Viewer

Одностраничное приложение на React и TypeScript: загружает JSON по сети,
показывает прогресс загрузки с кнопкой отмены и выводит 5 000 записей
в виртуализированной таблице с поиском и подсветкой совпадений.

Источник данных — публичный ресурс
[`/photos`](https://jsonplaceholder.typicode.com/photos) сервиса JSONPlaceholder:
5 000 объектов, около 1 МБ.

**Стек:** [Vite](https://vite.dev/) 8 · [React](https://react.dev/) 19 ·
[TypeScript](https://www.typescriptlang.org/) 6 ·
[TanStack Table](https://tanstack.com/table) 9 ·
[TanStack Virtual](https://tanstack.com/virtual) 3 · CSS Modules.

UI-библиотек нет: поисковый инпут и прогресс-бар — нативные
`<input type="search">` и `<progress>`.

## Быстрый старт

Два независимых способа, оба поднимают дев-сервер по адресу
**http://localhost:5173**. Порт у них общий, поэтому запускать оба сразу
не нужно.

### Локально

Нужен Node.js `^20.19.0 || >=22.12.0` (проверено на v24.5.0, npm 11.5.1).

```bash
npm ci
npm run dev
```

Остановить — `Ctrl+C`.

### В Docker

Нужен только Docker, устанавливать Node на машину не требуется.

```bash
docker compose up
```

Первый запуск собирает образ (`node:24-alpine`, `npm ci` внутри): сама сборка
занимает около 10 секунд плюс время на скачивание базового образа, последующие
запуски стартуют из кеша. Исходники подключены в контейнер bind mount'ом,
поэтому правка файла на хосте прилетает в браузер через HMR, без пересборки
образа.

Остановить — `Ctrl+C`, затем убрать контейнер и сеть:

```bash
docker compose down
```

## Как пользоваться

1. Нажмите **«Загрузить»** — начнётся загрузка `/photos`.
2. Пока идёт загрузка, доступна кнопка **«Отмена»**: запрос обрывается,
   приложение возвращается в состояние «Загрузка отменена» с кнопкой повтора.
3. После загрузки появляется таблица на 5 000 строк и поле поиска.
4. Наберите текст в поле — через 300 мс после последнего нажатия таблица
   отфильтруется по названию, а совпадения подсветятся жёлтым.

## Возможности

| Требование | Как сделано | Где смотреть |
| --- | --- | --- |
| Загрузка JSON | `fetch` с чтением тела через `ReadableStream`, затем рантайм-валидация `unknown` → `Photo[]`: ошибка формата не доезжает до таблицы | [`src/api/fetchPhotos.ts`](src/api/fetchPhotos.ts), [`src/api/parsePhotos.ts`](src/api/parsePhotos.ts) |
| Прогресс загрузки | Байты считаются по мере чтения чанков; нативный `<progress>` с подписью | [`src/components/ProgressBar`](src/components/ProgressBar) |
| Отмена | `AbortController`: сигнал уходит в `fetch`, аборт рвёт чтение тела и переводит состояние в `cancelled` | [`src/hooks/useJsonLoader.ts`](src/hooks/useJsonLoader.ts) |
| Виртуализированная таблица | TanStack Table для модели строк и колонок, TanStack Virtual для окна рендера: в DOM живут ~25 строк из 5 000, высота строки фиксирована (40 px), заголовок sticky | [`src/components/PhotoTable`](src/components/PhotoTable) |
| Поиск с подсветкой | Debounce 300 мс, регистронезависимое вхождение подстроки, совпадения оборачиваются в `<mark>` | [`src/hooks/useDebouncedValue.ts`](src/hooks/useDebouncedValue.ts), [`src/hooks/useFilteredPhotos.ts`](src/hooks/useFilteredPhotos.ts), [`src/components/Highlight`](src/components/Highlight) |

## Архитектура

```
src/
├── api/          загрузка и валидация: fetchPhotos, parsePhotos
├── hooks/        вся логика: useJsonLoader, useDebouncedValue, useFilteredPhotos
├── components/   презентационные компоненты, один компонент — одна папка
├── types/        Photo и LoaderState — контракты между слоями
├── App.tsx       сборка: состояние загрузчика, строка поиска, ветка с таблицей
└── index.css     цветовые токены --color-* и базовые стили
```

Правило разделения простое: **логика живёт в хуках, компоненты остаются
презентационными.** `App` не знает, как устроен `fetch`, а `PhotoTable`
не знает, откуда взялись данные и есть ли ещё загрузка — он получает готовый
массив и строку запроса.

Состояние загрузки — размеченное объединение
[`LoaderState`](src/types/loader.ts), а не набор булевых флагов:

```ts
type LoaderState<T> =
  | { status: 'idle' }
  | { status: 'loading'; progress: LoadProgress }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }
  | { status: 'cancelled' }
```

Благодаря этому `data` существует в типе только в состоянии `success`,
а `progress` — только в `loading`: невозможные комбинации вроде «идёт загрузка
и одновременно есть ошибка» не выражаются, а `switch` по `status`
в [`LoaderPanel`](src/components/LoaderPanel) проверяется компилятором
на полноту.

Хук [`useJsonLoader`](src/hooks/useJsonLoader.ts) параметризован функцией
загрузки, а не прибит к `fetchPhotos`: он умеет вести любой источник, который
принимает `AbortSignal` и сообщает прогресс, — хоть чтение локального файла.

Импорты внутри `src/` идут через алиас `@/` (например, `@/hooks/useJsonLoader`).
Алиас задаётся в двух местах сразу: `resolve.alias` в
[`vite.config.ts`](vite.config.ts) и `paths` в
[`tsconfig.app.json`](tsconfig.app.json).

## Принятые решения

- **Поиск идёт по полю `title`.** Это единственное поле со связным текстом:
  `url` и `thumbnailUrl` у всех 5 000 записей различаются только hex-цветом
  в конце, поэтому любая осмысленная подстрока (`via`, `placeholder`, `600`)
  матчит вообще всё, и поиск по ним вырождается.
- **«После окончания ввода» = debounce 300 мс.** Кнопки «Найти» нет: поиск
  стартует сам, когда пользователь перестал печатать. 300 мс — компромисс
  между «не дёргать фильтр на каждый символ» и «не заставлять ждать».
- **Фильтрация и подсветка используют одну и ту же строку запроса** — ту,
  что уже прошла debounce. Иначе подсветка обгоняла бы фильтрацию и мигала
  на неотфильтрованных строках.
- **Прогресс считается по байтам из `ReadableStream`,** а не по счётчику
  запросов или таймеру: это реальный объём, прочитанный из сети.
- **Внешние данные типизируются через `unknown` и явную проверку.** `any`
  в проекте нет; `parsePhotos` проверяет каждое поле каждой записи и бросает
  понятную ошибку с номером записи, если формат не сошёлся.
- **Доступность заложена, а не приклеена:** у прогресс-бара есть имя и подпись
  через `aria-describedby`, смены состояний и счётчик найденного объявляются
  через `role="status"`, таблица отдаёт `aria-rowcount` и `aria-rowindex`
  (иначе виртуализация врёт скринридеру о размере данных), а контейнер таблицы
  — отдельный табстоп, чтобы прокрутка работала с клавиатуры.
- **Мемоизации по месту нет, потому что она не понадобилась.** Профилирование
  прокрутки 5 000 строк дало медиану кадра 8,4 мс против 8,3 мс на холостом
  ходу — оптимизировать нечего.

### Почему прогресс без процентов

При загрузке вы увидите не «47 %», а счётчик прочитанных байт и полосу
в неопределённом состоянии. Это не недоделка, а свойство источника: проценты
требуют знать общий размер, то есть заголовок `content-length`, а JSONPlaceholder
его не присылает вовсе — ответ идёт по HTTP/2, сжатым (`content-encoding: gzip`)
и потоком, поэтому длина заранее не объявляется. Проверяется одной командой:

```bash
curl -sI https://jsonplaceholder.typicode.com/photos
```

Браузеру из этого ответа видны только `cache-control`, `content-type`,
`expires` и `pragma`. Причём даже пришедший `content-length` описывал бы
сжатый объём, а из потока читаются уже распакованные байты — поэтому
[`fetchPhotos`](src/api/fetchPhotos.ts) сбрасывает знаменатель, если прочитано
больше заявленного, и переключается на неопределённый прогресс.

Оба режима реализованы: если общий размер известен (другой источник, свой
бэкенд), [`ProgressBar`](src/components/ProgressBar) сам покажет проценты
и «X из Y»; если нет — честный счётчик байт вместо выдуманного числа.

## Качество кода

TypeScript настроен строго: `strict`, `noUncheckedIndexedAccess`,
`noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`.
ESLint работает на типах (`recommendedTypeChecked`) и вдобавок запрещает
дефолтные экспорты внутри `src/` — так имя сущности одинаково во всех местах,
где она импортируется.

### Тесты

[Vitest](https://vitest.dev/) с [Testing Library](https://testing-library.com/)
и jsdom; тестовые файлы лежат рядом с проверяемым кодом:

```bash
npm test
```

Покрыты три места, где ошибка не бросается в глаза: разбиение строки
на подсвеченные сегменты
([`Highlight`](src/components/Highlight/Highlight.test.tsx)),
задержка поиска после ввода
([`useDebouncedValue`](src/hooks/useDebouncedValue.test.ts)) и отмена загрузки
([`useJsonLoader`](src/hooks/useJsonLoader.test.ts)). Фейковый загрузчик
в последнем тесте обязан слушать `AbortSignal` — иначе он не воспроизводит
поведение настоящего `fetch`, и тест проходил бы по недоразумению.

Вместе с зависимостями `npm ci` ставит git-хуки (husky, скрипт `prepare`):

| Хук | Что делает |
| --- | --- |
| `pre-commit` | `lint-staged`: ESLint с `--fix` и Prettier по застейдженным файлам `src/` |
| `commit-msg` | commitlint: сообщение должно соответствовать Conventional Commits |
| `pre-push` | `npm run build && npm test`: ни сломанная сборка, ни упавший тест не уедут в удалённый репозиторий |

Разово обойти проверки — `git commit --no-verify`, `git push --no-verify`
или переменная окружения `HUSKY=0`.
